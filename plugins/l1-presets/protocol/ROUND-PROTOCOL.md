# 轮次协议（六步）

这条协议描述一轮工作从开工到关闭的固定流程。四个角色（plan / work / code / review）共用同一份，谁都不许改成自己方便的样子。
把它放到项目根的 `AGENTS.md` 里，四个角色都会自动读到（四个 preset 都挂了 `agent-instructions`）。

---

## 角色与链路

```
用户 ↔ plan → work → code → work → review → work → plan → 用户
```

| 角色 | 能做 | 不能做 |
|---|---|---|
| plan | 只读调研、写方案、派发 work、向用户交付 | 改文件、跑写入命令、替用户定预算/权限/业务规则 |
| work | 分派 code 与 review、跑授权范围内的验证、汇总 | 写源码（write/edit 已关闭）、改方案、换基线 |
| code | 写源码、写测试脚本、写启动说明、跑验证 | 越界改动（新依赖/新接口/新配置）、长期驻留服务 |
| review | 只读审代码、给结论 | 改产品、加测试、跑 shell、替 work 下结论 |

---

## 第 1 步 · 核对基线

**做**：读现状再说话。工作区状态、当前版本或提交、上一轮的遗留项、本轮要碰的文件现在长什么样。

**产物**：一句话写清「当前基线是什么」。后续所有「改了什么」都以它为参照。

**不过关的样子**：没看代码就给方案；把记忆里的版本当现状。

---

## 第 2 步 · 收敛方案与授权

**做**：把目标写成可执行、可验收的方案，并由用户授权。

方案至少包含：

- 目标与成功标准（怎么算做完）
- 改动清单：具体文件与位置，不是「相关模块」
- 明确不做的事（划边界比列表更重要）
- 验证方式：跑什么命令、看什么输出算通过
- 需要用户决定的：预算、新权限、新依赖、业务规则

**产物**：一份方案 + 一句授权。授权范围就是本轮的硬边界。

**不过关的样子**：方案里留「视情况」「酌情」；把需要用户拍板的事自己拍了。

---

## 第 3 步 · 连续实施（固定唯一 T0）

**做**：work 把源码任务派给 code，一次派一件事，同一时刻只有一个 code 在写。

**T0**：本轮唯一的基线标识（提交号或版本）。开工时定下，中途不换。确需新基线须先结束/停止当前轮，再明确授权新轮；不借阶段、重试、重建控制器或重新授权给原轮续期。

**产物**：T0 + 派发记录（派给谁、范围、验收条件）。

**不过关的样子**：写到一半发现基线不对就悄悄换；两个 code 同时写同一批文件。

---

## 第 4 步 · 限定修正

**做**：失败、重试、重启**累计计数**，同一个计数上判断，不许因为换了说法、重新派发、换个角色就清零。

建议阈值（可按项目调）：

| 情况 | 上限 | 到上限之后 |
|---|---|---|
| 同一测试/命令失败 | 3 次 | 停下来，写清卡点与已试方案 |
| 整体重跑 | 2 次 | 回 plan 复议方案，不要继续撞 |
| 服务重启 | 3 次 | 判定环境问题，上报 |

**产物**：计数器 + 每次失败的一句话原因。

**不过关的样子**：第 5 次重试还在说「再试一次」；把重启当成修复。

---

## 第 5 步 · 独立终审（证据分层）

**做**：review 独立看代码，给出三块结论——通过范围、未覆盖项、阻断项。

**证据分层**，不同层级不得互相扩大：

| 层级 | 能证明 | 不能证明 |
|---|---|---|
| 命令输出 | 这条命令在这个环境跑过且是这个结果 | 需求满足、边界情况正确 |
| 代码自述 | 作者说改了什么 | 真的改成了这样 |
| review 结论 | 它实际读过的文件与行为 | 它没读的部分 |

**产物**：review 的三块结论。有阻断项就退回第 3/4 步。

**不过关的样子**：用 code 的「已完成」当终审；把「测试通过」写成「需求满足」。

---

## 第 6 步 · 交付并关闭

**做**：给出固定结构的交付，然后把这一轮关掉。

```
版本：<提交号/版本号>（T0 → 本轮结束）
结果：<做了什么，验证过什么>
未覆盖项：<没做的、没验的、证据不足的；没有就写「无」>
费用：<已知累计用量、pending 部分、可得金额；金额未知写 unknown，不填 0>
已停止的服务：<确切身份与退出证据；accepted/inactive/查不到都不是已停，无证明写 pending/unknown>
```

**不过关的样子**：只写「已完成」；未覆盖项留空当没有；自己起的服务还在跑。

---

## 阻塞与上交

**局部阻塞** → 保存证据，继续做其他部分，最后一并说明。不要因为一个点卡住就整轮停摆。

**必须上交用户** → 只限三类：

1. 需要新权限（越出当前沙箱或授权范围）
2. 需要新预算（超出本轮约定）
3. 需要新业务规则（方案里没覆盖的判断）

其余问题自己解决，或按第 4 步的阈值停下说明。不变前提不反复要求用户确认；NOT_GATED 也不表示安全或可以忽略问题。accept 只用于最终收尾。

## 与 L2 候选版共同运行时

- 派发/复用/停止通过受控 chain 工具，不调用同名 Team/native 入口绕过管理。work 同轮复用，code 按稳定任务族，review 独立；忙或取消时不能新建替身。
- 先持久停止原因、范围及稳定 requestId，再发信号；原生启动封闭与 Agent/job 退出分别确认。锁超时只表示意图已写，已进入创建区的操作可能仍在进行，不把 pending 改写为 stopped。
- 计算需要完整只读隔离。当前安装 Windows provider 为 partial，L2 因而拒绝启动；不得改用裸 shell、远程回退或另开代理绕过。
- 日常汇报只用目标/T0、执行、预算、交付、阻塞、下一步六字段；需要详细账本时才展开。
- 关闭/停止的根会话不自动恢复。下一轮当前需要新的根 plan 会话；close 工具回执是收尾产物。

L1 独立运行不具备 L2 的持久控制器保证。候选版覆盖与限制以 [L2 验收说明](<../../l2-protocol/ACCEPTANCE.md>) 为准。
